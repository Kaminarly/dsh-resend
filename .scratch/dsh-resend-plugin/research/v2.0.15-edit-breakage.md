Scope: read-only diagnosis. Nothing was installed, run, or modified.
Every claim is tagged **verified-from-code** (I read the line), **from-docs** (primary source
says it), or **inferred** (my reasoning, not directly attested).

## Verdict

**The leading hypothesis is falsified.** The Conversation-Definition / new-Chat-node-kind path
did *not* change in a way that breaks `dsh-retrace@0.4.32` on v2.0.15. The plugin's own client
telemetry — written to the host log by the shipped build — reports
`definitions=4 slots=6 seats=6 uiConversationSource=uiConversation.events` on
`DSHDesktop/2.0.15` (`LOG\dsh-2026-09-28.log:108`, `:143`, `:182`, `:237`).
That means, **verified-from-code**: the registration entry point `ctx.uiConversation.events.register`
exists and was reached (`uiConversationSource=uiConversation.events`, *not* the
`.no-register-entry` failure value at `PLG\lib\client.js:3967`); all four Definitions registered,
including `userActionsDefinition`; and all six slot mounts succeeded, including the three
`conversation.chat.node` keyed registrations (`user-actions`, `retrace-reference`,
`recall-marker`). The service name is unchanged (`super(ctx, "uiConversation")`,
`PKG\dsh-client-ui-conversation\lib\client.js:3043`) and `events.register` is still the sole
official Definition registry (`…\README.zh.md:28`). `ChatNodeKind`'s key table is a
**type-level and documentation** constraint, not a runtime gate: `dsh-client-ui-slots`
accepts any keyed slot key and rejects only a *duplicate* key at the same priority
(`PKG\dsh-client-ui-slots\lib\index.js:175-179`), and the dispatcher carries a `fallback`
precisely so an unoccupied kind still renders
(`PKG\dsh-client-ui-chat\lib\client.js:1770-1778`). The historically documented causes of this
*exact* symptom were fixed in 0.4.28 and are present in 0.4.32: `@deepseek-ai/dsh-session`
removing `Session.events` (absorbed by `PLG\lib\host-compat.js:75-159`) and the plugin's own
read of a non-existent `snapshot.chat.nodes` (upstream CHANGELOG 0.4.28, **from-docs**).
Consequently the failure is **not** "the Definition path is dead", and the reported
"Recall works" cannot mean *user-message* recall: in `UserActionsRow` the 编辑/Edit and
撤回/Recall chips are two unconditional children of one `<span>`, behind one shared early
return (`PLG\lib\client.js:1196`, `:1278-1295`) — **verified-from-code** — so they cannot fail
independently. "Recall works" can only be the assistant-reply recall ↩, which lives in the
separate `AssistantActions` component on the plain list slot (`PLG\lib\client.js:1137-1146`).
The single code path where *edit* diverges from recall and regenerate is the host-side
`isRoundBoundary` gate, used by `editAndResend` alone (`PLG\lib\host-core.js:501`; recall has
no event-type check at `:460-472`; regenerate checks `assistant/message` at `:553-555`), and
`isRoundBoundaryEvent` is `event?.type === 'user/message' && event?.data?.source?.kind === 'user'`
(`PLG\lib\span-semantics.js:74-75`) — **verified-from-code**, labelled *hypothesis* because no
op invocation exists in any log to confirm it fired.

**Minimal API delta a new plugin must target** (all verified-from-code):

1. Register Definitions via `ctx.uiConversation.events.register(def)` — the service is still
   `uiConversation` (`PKG\dsh-client-ui-conversation\lib\client.js:3043`), the registry is
   `service.events` (`:3045`), `register` keys by `definition.kind` (`:2656`), and
   `target`/`buildViewNode` must be declared together (`:2688-2690`).
2. Manufacture new Chat node kinds freely; dispatch key is the **node's** `kind`, not the
   Definition's (`PKG\dsh-client-ui-chat\lib\client.js:1770-1771`). The fixed `ChatNodeKind`
   list is documentation/typing only. Keep the node shape exactly
   `{key, kind, id, target:'chat', anchorSeq, location, visibility, data}`
   (`PKG\dsh-client-ui-chat\lib\client.js:7143-7154`); `buildNode` asserts `node.key === context.key`
   and `node.target === target` (`PKG\dsh-client-ui-conversation\lib\client.js:2436-2442`).
3. `seq`-based anchoring including the `seq - 0.5` trick still works — `anchorSeq` is documented
   as the "sortable render position" and is never integer-validated
   (`PKG\dsh-client-ui-chat\lib\client.js:7138`, `:7149`; `PKG\dsh-client-ui-conversation\lib\client.js:2436-2442`).
4. Read session events only through `snapshotEvents()` / `eventAt(seq)`
   (`PKG\dsh-session\lib\index.js:1323-1357`); `Session.events` is gone. Do not index a
   snapshot array positionally by `seq` without an `eventAt` first attempt.
5. Gate user-message operations on the *event*, not on an index: fetch the event and test
   `type === 'user/message' && data.source?.kind === 'user'`, and prefer a fallback that does
   **not** silently abort when the read is ambiguous — `editAndResend`'s
   `not-user-message` throw (`PLG\lib\host-core.js:501-503`) is exactly where a new plugin
   should degrade to a retryable `message-pending` instead.
6. Do **not** register `conversationEvents` in a static `inject`, and expect the packaged
   double-mount hazard (see §7).

## 4. Anchoring

`seq`-based anchoring survived, including `seq - 0.5`.

- `anchorSeq` is documented as "sortable render position" and accepted as an arbitrary number —
  `@param anchorSeq - sortable render position` (`PKG\dsh-client-ui-chat\lib\client.js:7138`),
  assigned verbatim (`:7149`). **verified-from-code.**
- Nothing validates its integrality: not `chatNode` (`:7143-7154`), not `buildNode`
  (`PKG\dsh-client-ui-conversation\lib\client.js:2436-2442`). Contrast with `seq` elsewhere,
  which *is* constrained (`isEventSeq`, `PKG\dsh-session\lib\index.js:286-288` — non-negative
  safe integer). **verified-from-code.**
- The plugin's reference row is the only user of the half-integer:
  `chatNodeLike(context, 'retrace-reference', context.state.seq - 0.5, context.state)`
  (`PLG\lib\client.js:646`). **verified-from-code.**
- Upstream documents that this trick needed a matching read-side rule, and that it has one:
  "`retrace-reference` 节点锚定 `seq - 0.5`(半整数)…现在半整数锚点映射回整数 seq 匹配;
  ReferenceRow/UserActionsRow 按真实消息 seq 判定" (CHANGELOG 0.4.5, **from-docs**). The client
  code agrees: `ReferenceRow` judges hiding by the real message `seq` from `node.data`, not by
  the anchor (`PLG\lib\client.js:1161-1171`), and the shadow lookup maps to the first
  non-marker node at the integer seq (`:917-922`, `:930-934`). **verified-from-code.**
- No new ordering mechanism was introduced that supersedes `anchorSeq`; the seat's flow keys are
  the node key, not the anchor (`data-chat-anchor-key` / `data-chat-flow-key` both = `flowKey`,
  `PKG\dsh-client-ui-chat\lib\client.js:1756-1763`). **verified-from-code.**

Conclusion: anchoring is **not** the breakage. **verified-from-code.**

## 7. Verdict for our spec — what a new plugin must do differently, and what else is threatened

### 7.1 What a new plugin must do differently so user-message editing works on v2.0.15

Nothing about the Definition / node-kind mechanism needs to change; it is intact and exercised
(§1, §3). The real targets are the *edit-specific* gates and the *diagnosability* of the read
path:

1. **Do the event-type gate on a freshly read event, and make its failure non-silent and
   retryable.** `editAndResend` is the only op that requires
   `isRoundBoundary(eventAt(session, seq))` (`PLG\lib\host-core.js:501`) where
   `isRoundBoundaryEvent` = `event?.type === 'user/message' && event?.data?.source?.kind === 'user'`
   (`PLG\lib\span-semantics.js:74-75`), and it throws the terminal, non-retryable
   `not-user-message` / "Only user messages can be edited and re-sent."
   (`:501-503`). **verified-from-code.** A new plugin should (a) resolve the event via
   `eventAt(seq)` and, only then, (b) test the type; and on a miss distinguish
   "read is stale/sparse" (retryable `message-pending`) from "genuinely not a user message"
   (terminal). Upstream already established that vocabulary for the span path
   (CHANGELOG 0.4.24, **from-docs**) but the type gate itself has no such branch.
2. **Never index the snapshot array positionally without `eventAt` first.**
   `host-compat.js:158` ends with `return sessionEvents(session)[seq]` — if `session.eventAt`
   is absent or returns `undefined`, the fallback assumes the snapshot is dense and seq-indexed.
   `eventAt` **does** exist (`PKG\dsh-session\lib\index.js:1323`), so the happy path is fine;
   but the plugin's own comments repeatedly record that the in-memory host event view is
   windowed with `undefined` holes (e.g. `PLG\lib\host-core.js:246-248`, `:566-568`), which is
   exactly the condition that makes the fallback return `undefined` → `isRoundBoundary(undefined)`
   → `false` → `not-user-message`. **verified-from-code** for the code; **inferred** as the
   failure mechanism.
3. **Do not gate edit and recall in one component.** The plugin's design makes the edit chip
   and the user-recall chip co-fatal (`PLG\lib\client.js:1196`, `:1278-1295`) — **verified-from-code** —
   which is why this symptom is so hard to attribute. Separate surfaces, or at minimum
   independent boundaries, so a single throwing read cannot remove both affordances.
4. **Keep the node shape and anchoring as-is.** `{key, kind, id, target:'chat', anchorSeq, location,
   visibility, data}` with node-`kind` dispatch and the `seq - 0.5` anchor are all still valid
   (§3, §4). Do not "fix" them.
5. **Wrap each surface in your own error boundary** — the plugin does (`withPanelBoundary`,
   `PLG\lib\client.js:3321-3328`) and that is what turns a silent host-boundary swallow into a
   visible panel. The titles it would show are the discriminator to look for:
   `panel.error.userActions` = "用户消息操作渲染出错" / "User message actions failed to render"
   (`PLG\lib\client.js:233` / `:381`), `panel.error.actions` = "消息操作按钮渲染出错" /
   "Message action strip failed to render" (`:232` / `:380`). **verified-from-code.**
   A missing row with *no* such panel points at `match()`/`buildViewNode()` returning null
   instead; a panel points at a throwing render.

### 7.2 Deltas that would *also* threaten the new plugin's regenerate or rollback

1. **`isRoundBoundary` is also load-bearing for regenerate, indirectly.**
   `regenerate` validates `args.span.start` with it (`PLG\lib\host-core.js:577`) and uses it to
   walk back to the round's user message (`:586-587`). So the same fragile read can silently
   downgrade regenerate to `no-prompt` ("No user message precedes this reply; cannot
   regenerate.", `:591`, `:598`) rather than editing. **verified-from-code.** Do not assume
   regenerate is immune just because it "works" today.
2. **`sourceEventSeqs` completeness is now a hard rejection**, not a warning: a replace whose
   `sourceEventSeqs` omits any shadowed node throws
   (`PKG\dsh-session\lib\index.js:327-328`, `assertSourceEventReferences`). Both the edit and
   regenerate write paths go through the same marker writer
   (`PLG\lib\host-core.js:526`, `:615`). Any new plugin writing replacement carriers must cite
   the audit seq **and** every shadowed node — the plugin documents this contract at
   `PLG\lib\marker-carrier.js:33`. **verified-from-code** for the host rule; **from-docs** for
   the plugin's compliance.
3. **The replace shape is now exactly three keys.** `isReplaceOp` requires `Object.keys(op).length === 3`
   with `op`/`startSeq`/`endSeq` (`PKG\dsh-session\lib\index.js:290-293`). Adding a fourth key
   (e.g. a provenance field) throws. **verified-from-code.**
4. **Non-surface-eligible events may not carry `surfaceOp` or `sourceEventSeqs`**
   (`PKG\dsh-session\lib\index.js:298-301`). The audit segment (`compaction/prune`) must stay
   bare. Rollback writes the same two-segment carrier, so this constrains rollback too.
   **verified-from-code.**
5. **`assistant/message` can never carry `sourceEventSeqs`** — hard throw
   (`PKG\dsh-session\lib\index.js:313`). Any design that tries to hang provenance on an
   assistant message is structurally impossible; this is why the plugin uses `user/message`.
   **verified-from-code.**
6. **The observed double-mount, and the current unmounted state — both real, both important.**

   **verified-from-code**, `LOG\dsh-2026-09-28.log`:
   ```
   :112 [W] [client-module-registry] Error: client-modules: package dsh-retrace resolves from
       multiple active Loader sources: "…/profiles/desktop/node_modules/dsh-retrace/lib/index.js"
       from …/profiles/desktop/.dsh-market/, "dsh-retrace" from …/profiles/desktop/; remove one entry
   :120 [W] [dsh-retrace] dsh-retrace: route registration failed: Error: webserver: duplicate
       prefix route "/api/plugins/retrace"
   :130 [I] [dsh-retrace] retrace: versioning disabled: DomainError: domain 'retrace' is already open
   ```
   A package reachable from two loader sources mounts the host half twice. Consequences visible
   here: the HTTP data channel fails to register, and the `retrace` storage domain refuses to
   open, so the versioning/projection channel degrades. For the plugin that is survivable because
   the *first* mount wins and the second's Definition/slot registrations throw on duplicate keys
   (`PKG\dsh-client-ui-conversation\lib\client.js:2623-2624`;
   `PKG\dsh-client-ui-slots\lib\index.js:178`) — but a new plugin must register its own data
   channel and storage domain **idempotently across mounts** (e.g. tolerate
   `domain … is already open`), or it will lose timeline/rollback the same way. **verified-from-code**
   for the log evidence; **inferred** for the "first mount wins" reconciliation.
7. **The plugin is currently not mounted at all.** `PLG`'s row exists in the profile's
   `dependencies` (`C:\Users\Administrator\.dsh\profiles\desktop\package.json:9`,
   `"dsh-retrace": "0.4.32"`) but **not** in `dsh.profile.bundles` (`:15-24`), and the profile's
   patch layer reports `[root] patch: entry "dsh-retrace" not found` on every start after
   15:44 (`LOG\dsh-2026-09-28.log:251`, `:255`, `:261`). **verified-from-code.** Practical
   consequence: any live reproduction attempt right now will observe *no* retrace UI at all,
   which is not the symptom under investigation. Restore the bundle entry before re-testing.

### 7.3 What the evidence says about *how* it fails

The task asked to establish the mode if possible. From primary sources:

- **No retrace op was ever invoked** in any session in the available logs. The wrapper logs

  as far as submitting an edit *and* never triggered regenerate or recall either — meaning the

  and is not corroborated by host-side evidence here.
- Therefore the mode is **not established** from these logs, and I will not assert one.
  The three candidate modes with their distinguishing signatures, for the next person to check:
  - *affordance missing, no error panel* → `match()` or `buildViewNode()` returning `null`
    (`PLG\lib\client.js:596-616`, `:644-647`) or `useSeqHidden`/`useShadowed` returning true
