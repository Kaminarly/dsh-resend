# 文件回滚存储：一手资料研究

研究日期：2026 年 10 月 13 日。范围：核对本项目现有存储，比较差分、Git pack、压缩内容存储和内容分块。本文不修改运行代码，不操作已安装插件的私有数据，也不提供未经实验验证的空间收益。

完成标准：每项外部技术结论有可核验的一手资料；说明恢复所需的基准、清理依赖和故障边界；明确哪些是已确认事实，哪些是本项目的设计建议。

## 结论

可以保存差分。有两种可行方向：「独立可恢复的基准内容 + 字节差分 + 有限链长」，以及「当前文件 + 反向字节差分」。前者也可以使用 Git 已有的 pack 差分能力。现有接口读取完整版本，磁盘上不必按完整原文保存每个版本。Git pack 本身就可以通过差分重建完整对象。[Git pack 格式](https://git-scm.com/docs/gitformat-pack)

若保持现有独立历史快照接口，可以复用 Git pack 的成熟字节差分；私有裸仓库也能接收普通目录文件的内容，不要求工作目录本身是 Git 项目。缺少 Git 可执行程序时再使用独立压缩 CAS。若选择专门面向撤销的接口，也可研究「当前文件 + 反向字节差分」，它在严格校验修改后状态的前提下能够成立。两条路线都需要同步改造清理与空间统计。当前代码不能只追加一条 `git repack` 命令。

这不是对空间收益的定量承诺。实际收益需要用相同文件、版本序列、压缩参数和完整回读验证比较。

## 本项目现状

以下事实来自本地代码，可直接检查：

- `src/file-snapshots.js`：Git 项目使用插件私有裸仓库 `objects.git`，通过 `hash-object -w --stdin` 写 blob，再通过 `cat-file blob` 读取。没有创建引用、树或提交，也没有执行 pack。
- 同一文件中，非 Git 项目使用 `objects/<SHA-256>`，直接写原始字节。同样内容使用相同地址；已存在文件不再写入。
- `src/file-observations.js`：每个受支持的写入保存 `before` 和 `after` 的内容地址。后续重新读取观察记录时需要将两个地址恢复为完整字节。
- `src/file-rollback.js` 和 `src/rollback-files.js`：恢复前检查当前文件是否与 `after` 完全一致；写入完整 `before`；替换前再检查，替换后核对结果。文件不存在用 `null` 表示，不能与零字节文件混淆。
- `src/storage-cleanup.js`：扫描原始 CAS 文件和 Git loose object 的两位前缀子目录。它不枚举 `objects.git/objects/pack` 内的对象，也不统计或重写 pack。
- `src/private-storage.js`：已有跨进程锁和会话活动登记，但压缩任务仍需明确与所有内容写入、读取和清理共享的协调边界。
- `package.json` 声明 Node.js `>=22`。此次研究环境为 Node.js `v22.22.1`、Git `2.52.0.windows.1`；这不代表所有 DSH Desktop 宿主都具备同样版本。

Git loose object 已经过 zlib 压缩，并不是完全未压缩的文件副本；目前缺少的是跨相似版本的差分打包。非 Git CAS 的原始字节尚未压缩。[Git 官方：对象内部存储](https://git-scm.com/book/en/v2/Git-Internals-Git-Objects)

连续修改 `A → B → C` 时，内容寻址会复用相同的 `B`。因此现有方案不是每次都重新存两份完全独立副本；新版本之间仅有少量不同的情况下，它仍会保存不同版本的完整表示。

## 方案比较

| 方案 | 空间来源 | 恢复与清理要求 | 本项目适用性 |
|---|---|---|---|
| 逐对象压缩 CAS | 单个内容的重复模式；仍保留已有相同内容去重 | 每对象可独立恢复；解压后校验原始内容地址 | 增量最小，适合先改善非 Git 项目 |
| Git pack | 独立压缩或相似对象差分；集中存储减少对象文件数 | 保护外部 JSON 引用；清理需要重写 pack 或分组管理 | 可复用成熟差分格式，但不能沿用现有 loose 清理 |
| 基准 + 字节差分 | 只编码与基准不同的字节 | 必须保存基准和依赖闭包，限制链长；删除会话不能删掉别人的基准 | 可统一 Git 与普通目录，但需要新的存储格式和垃圾回收 |
| 当前文件 + 反向差分 | 借用当前文件作为基准，存回退所需差异 | 当前文件必须仍是精确的修改后版本；长期历史重建更复杂 | 单步撤销可以成立，不能直接替换现有持久化接口 |
| 内容定义分块 + 压缩 CAS | 多版本共享相同内容块 | 保存块清单，按块引用回收；大量小块会增加索引和文件数量 | 适合大文件反复局部修改，应有实际规模证据再引入 |

表中的适用性是根据本项目代码作出的判断，不是官方资料对本插件的评价。

## Git pack：能复用差分，但先解决生命周期

### 已确认能力

`git pack-objects` 接收显式对象列表，生成 pack 和索引，Git 可按原始对象地址读取。对象可保存为压缩完整内容或另一对象的差分。正常磁盘 pack 应独立完整；不要使用需要外部基准的 thin pack 作为私有存档。[git-pack-objects](https://git-scm.com/docs/git-pack-objects)

pack 差分用「复制基准某段字节」和「插入新字节」重建对象。基准还可以是另一个差分，但最终必须能恢复出完整内容；对象地址按重建后的完整内容计算，外部 JSON 中的 `git:<OID>` 不必因打包而改变。[Git pack 格式](https://git-scm.com/docs/gitformat-pack)

`--window` 决定相似对象候选窗口，`--depth` 限制差分链深度；深链会增加读取工作。`--window-memory` 和线程数共同影响内存。`repack` 默认启用较紧凑的基准偏移表示，并不是要另行发明差分格式。大于 `core.bigFileThreshold` 的对象不会使用差分压缩。[git-repack](https://git-scm.com/docs/git-repack)

本项目的实验可以比较较浅链深和受限窗口内存，但参数应由测量决定。不要把最大窗口、最大深度或最高压缩级别当成桌面插件默认值。

### 当前无引用 blob 的风险

`hash-object -w` 只写对象。读取标准输入时默认不应用文件过滤与行尾转换，这与目前按原始字节保存的意图一致。[git-hash-object](https://git-scm.com/docs/git-hash-object)

插件 JSON 中保存的 OID 不属于 Git 可达关系。`gc` 保护 `refs/*`、索引、reflog 等认识的引用，但不知道本插件 JSON；并发写入尚未建立引用时也存在删除风险。[git-gc](https://git-scm.com/docs/git-gc)

普通 `repack -a` 围绕 Git 引用组织对象；`--keep-unreachable` 可保留不可达对象，却把应回收对象也一起保留，不能替代会话级生命周期。cruft pack 同样涉及不可达对象过期规则。因此不能直接对现有私有裸仓库执行 `gc --prune=now`，也不能认为 `repack -ad` 会安全压缩 JSON 所需的全部内容。[git-repack](https://git-scm.com/docs/git-repack)

可选设计：

1. 将每个被保留的内容地址建立为私有 `refs/rollback/...` 引用，或者让会话私有树引用其内容。引用更新与 JSON 发布必须有可恢复顺序，避免 JSON 已可见而保护尚未生效。`update-ref --stdin` 可批量修改引用，并支持检查旧地址。使用自定义引用命名空间，不能把 blob 放进要求提交对象的分支命名空间。[git-update-ref](https://git-scm.com/docs/git-update-ref)
2. 由插件在独占维护中收集保留 JSON 的完整对象清单，显式交给 `pack-objects`，验证所有对象回读后发布新存储代。插件独占管理 pack，不允许普通 Git 维护任意淘汰这些对象。这是设计建议，仍需要崩溃恢复、旧存储代回收和并发测试。

`pack-objects --all` 枚举的是 `refs/` 下的引用，不会查找插件 JSON 中的 OID。`--all` 无法自动弥补当前缺少引用的问题。[git-pack-objects](https://git-scm.com/docs/git-pack-objects)

### 私有裸仓库可用于普通目录

`git init --bare <directory>` 创建独立裸仓库；`hash-object` 可从标准输入写 blob，文件也可以来自工作树外。因此「只在 Git 项目使用私有 Git 内容存储」是当前插件的选择，不是 Git 技术限制。[git-init](https://git-scm.com/docs/git-init)、[git-hash-object](https://git-scm.com/docs/git-hash-object)

此次在隔离临时目录进行了最小验证：创建私有裸仓库；输入包含 UTF-8 BOM、中文、CRLF 和 NUL 的字节；将 blob 写入 `refs/rollback/<OID>`；检查 `rev-list --objects --all`；执行 `repack -ad`；最后 `cat-file blob` 回读。结果：自定义引用成功，`--all` 包含该 blob，loose 对象数为 0、pack 内对象数为 1，回读与输入逐字节一致。临时目录已删除。该实验没有接触用户工作文件或已安装插件私有数据，仅证明当前 Git 版本支持这条最小路径。

### 清理冲突

`prune-packed` 删除已经在 pack 中存在的冗余 loose 副本，不负责删除不再被插件需要的 packed 对象。[git-prune-packed](https://git-scm.com/docs/git-prune-packed)

当前清理按每个对象文件的字节数计费、预览、核验并删除。打包以后：

- 同一会话原来关联的 loose 文件可能消失，空间统计会漏掉 pack。
- 删除 JSON 和 loose 文件不能释放 pack 中的相应内容。
- 不能为了删除某个会话直接删共享 pack，否则会删除其他会话仍使用的内容。
- 清理预估应区别「逻辑引用内容」「共享物理存储」「这次实际释放字节」。实际释放往往需要重写 pack，且必须预留重写所需空间。

这些结论来自现有扫描方式和官方 pack 结构；收益估计不能直接采用 Git 对象的未压缩长度。

## 只保存 diff：先明确从哪里恢复基准

### 反向差分的成立条件

若保存 `修改后 → 修改前` 的差分，当前文件恰好等于修改后版本时，可以据此撤销；不必为了单次撤销再保存另一份修改后全文。但需要先校验修改后内容的精确长度和加密摘要，并验证恢复结果的摘要。

这与现有「文件被外部改动就拒绝覆盖」的策略可以相容。新建文件撤销若仅执行删除，可保存「修改前不存在」与修改后长度、摘要，不必为该删除动作保存新文件全文。对于多次修改，可从经过校验的最新版本逐步逆推，各步检查目标摘要；重启并不必然破坏这种策略，因为修改后文件本身可以继续作为基准。

问题在于，当前观察记录重放和快照接口要求脱离工作目录也能读取完整 `before`、`after`。用当前文件作为唯一基准会改变这一能力；遇到同文件多次修改、跨会话修改、回滚某段历史或清理中间会话，还必须定义链和分支处理规则。需要重构观察重放、预览准备和恢复流程，而不是只替换 `snapshots.get`。

所以「只记录 diff」不是无需基准。它可能把基准存到别处，或把依赖转移给仍可能被修改、删除的工作文件。对于持久历史，建议至少保留一份插件自己管理的独立基准。

### 建议的持久差分形式

保存完整基准及差分对象，元数据包含格式版本、基准内容地址、目标完整内容地址、原始长度、压缩方法和差分方向。内容身份始终取原始完整字节摘要，存储表示可以是 raw、压缩全文或压缩差分。

编码层选择字节范围操作，不将任意文件先解码成字符串。VCDIFF 规范提供 `ADD`、`COPY`、`RUN` 这类按字节重建的操作，其窗口选择影响编码大小，但解码端不用重复编码算法。[RFC 3284](https://datatracker.ietf.org/doc/html/rfc3284)

本项目的设计建议：

- 限制差分链深，达到阈值重新保存完整基准，避免恢复要逐一穿过整个会话历史。
- 对每个候选比较「压缩全文」和「压缩差分 + 元数据」的真实尺寸，后者没有优势就保存全文。完全重写、短文件和已压缩文件都需要此回退。
- 清理从保留记录开始遍历内容及其基准依赖，保留全部依赖闭包。共享基准不能随着某个会话被删掉；必要时将其依赖者改写成独立基准。
- 所有恢复后内容重新校验地址和长度；损坏、缺基准、循环引用、超长链或越界差分一律拒绝写回工作文件。

这些策略仍需实现和验证；RFC 不会自动提供插件的垃圾回收或崩溃恢复。

### 中文、BOM、CRLF 和二进制保真

字节差分可以保留 UTF-8 中文、UTF-8 BOM、CRLF、无末尾换行、NUL 和任意二进制内容；前提是整个保存、差分、压缩、重建流程不做字符串重编码或行尾标准化。这是字节重建机制的推论，需要用真实字节相等验证。

普通展示用文本 diff 不应直接承担存档格式。补丁系统还有空白处理、上下文匹配和末尾换行处理；`git apply --whitespace=fix` 甚至会主动改空白。若采用文本补丁，必须证明生成及应用端无损并禁用会改变内容的处理，二进制另有编码。[git-apply](https://git-scm.com/docs/git-apply)

## 压缩 CAS：适合先做的改进

Node.js `node:zlib` 已有 Brotli API。原生 Zstandard API 于 `v22.15.0` 和 `v23.8.0` 加入，当前官方文档仍标记为实验性；因此 `engines: >=22` 不能保证全部宿主具备 Zstandard。可先使用兼容范围更广的 Brotli，或运行时检测并提供固定可读的回退格式。[Node.js zlib](https://nodejs.org/api/zlib.html)

Zstandard 是无损压缩，压缩级别可调整，也可使用字典；字典可以共享相似内容的模式，但字典本身需要保存且可用，不能误把跨版本重建依赖当成普通独立压缩。[Zstandard 官方项目](https://github.com/facebook/zstd)

本项目建议：压缩地址保持「解压后的完整原文摘要」，对象头记录版本、算法和原始长度；读取后沿用目前的摘要校验。对压缩后更大的内容保存 raw；解压设置上限，避免损坏头声明异常大的输出。每个对象独立压缩可以保持现在简单的按引用清理，但不能去除相似版本间重复的数据。

## 内容分块：后续选项

Borg 官方说明，固定分块按位置切分；内容定义分块按滚动哈希选择边界，前方插入或删除内容后，未变化区域更容易形成相同块。去重身份使用强哈希，而不是切块用的滚动哈希。[Borg 数据结构](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)

本项目若处理很多大文件，可将版本保存为块地址列表，对块独立压缩去重。这样不需要版本差分链，但会增加块清单、索引、对象数量和引用扫描成本。普通代码文件是否值得采用，必须由代表性实验确认；不应照搬备份软件的块大小默认值。

## 必须补齐的验证

实现前的基准至少包括短文件、大段重复文本、普通源码、每版局部修改、每版全面重写、随机二进制、已压缩文件和中文/BOM/CRLF。按原始字节比较所有版本完整回读结果，同时记录对象、索引、元数据合计磁盘字节和写入、恢复耗时。

实现后的正确性验证还需包括：重启恢复；共享基准跨会话保留；清理中间版本后其余版本恢复；并发写入与维护；压缩发布各步骤中断；数据损坏、缺基准、磁盘不足；继续读取旧版 `cas:`、`git:` 数据。既有数据应先完整回读并核验，再切换；不能先删旧内容再验证新表示。

以上是建议的验收条件，本文没有声称已完成这些新格式验证。空间基准与最终选型应由独立实验报告补充。
