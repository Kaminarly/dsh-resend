# 文件回滚存储节省空间方案研究

日期：2026-10-13。范围：现有文件回滚、重启恢复、内容保真、共享数据清理及旧记录兼容。本文是研究与选型建议，未修改运行代码、已安装插件或真实回滚数据。

## 结论与建议

可以改用差异存储，而且局部修改的收益明显。需要先区分两个目标：

- **安全撤销文件修改**：只在当前文件仍与助手修改后内容一致时还原。这是现有回滚规则。可以保存逆向字节差分，借助当前工作文件重建修改前内容。
- **独立保存任意历史文件版本**：不依赖工作文件仍然存在或保持一致。需要插件自己保存完整基准，再保存差分；Git pack 是已有的成熟实现。

针对目前产品，我更倾向第一种目标，采用「逆向字节差分为主，必要时保存压缩后的修改前全文」；继续拒绝覆盖用户后来修改的文件。对于新建文件，只需不存在标记及修改后内容的长度、摘要。如果希望同时保留独立历史内容读取能力，应选择私有 Git pack 或完整基准加有界差分链。

这是基于现有代码和下述实验的设计建议，不是已确认的产品决定。迁移不能只替换 `snapshots.get`：现有观察重放、预览准备和数据清理都需要适配。

## 当前方案的浪费在哪里

[file-snapshots.js](../src/file-snapshots.js) 对普通目录保存原始全文；Git 项目写入私有 loose blob，压缩每份全文，但没有做跨版本差分。相同内容会去重，相似内容仍占独立对象。

[file-observations.js](../src/file-observations.js) 持久保存每次工具操作的 before/after 引用；后续调用复用相同对象，所以连续修改 20 次一般是 21 个不同内容版本，而不是 40 份。重启修复需要的是可靠的持久记录，并不要求每个版本在磁盘上独立保存全文。

现有 [rollback-files.js](../src/rollback-files.js) 明确要求当前内容与记录的修改后内容一致，才允许写回。这个规则使逆向差分具备成立条件。也正因为当前只提供安全回滚，而非独立历史浏览，新建文件删除并不一定需要保存它的全文副本。

## 可复现空间实验

执行命令：

```powershell
node .scratch/dsh-resend-storage-research/benchmark.mjs
```

脚本：[benchmark.mjs](../.scratch/dsh-resend-storage-research/benchmark.mjs)。完整结果：`output/rollback-storage-research/results.json`；最终运行输出：`output/rollback-storage-research/benchmark.log`。实验使用 Node.js v22.22.1、Git 2.52.0.windows.1，固定输入与参数，只在独立临时目录操作；结束时删除临时数据。

每个场景包含初始版本及 20 次修改，共 21 个不同版本。比较原始全文、Zstandard level 3 压缩全文、压缩字节差分加每 8 版基准、逆向字节差分、现有 Git loose 以及 Git pack。Git pack 使用显式内容地址列表、window 50、depth 8、单线程，包含 `.pack` 和 `.idx`。

下面统计的是文件长度总和，不是磁盘分配空间。共同的会话观察、回滚清单和完成记录未计入；差分方案新增的基准索引或前后摘要索引已计入。Git 仓库基础文件约 26 KiB，表中未计入。逆向差分依赖当前工作文件，其他列保存独立版本，能力不同，不能只根据最小数字判断等价。

| 样本及修改方式 | 普通目录现状：原始全文 | Git 项目现状：逐份压缩 | 独立压缩全文 | Git 差异打包 | 逆向差分：依赖当前文件 |
|---|---:|---:|---:|---:|---:|
| 186 B 中文短文件，每次改 1 B | 3,906 B | 1,964 B | 1,818 B | 2,408 B | 3,741 B |
| 本仓库约 25 KiB 源码，每次改 1 B | 542,955 B | 131,979 B | 120,394 B | 7,460 B | 3,741 B |
| 1 MiB 重复较多的源码样本，每次改 1 B | 22,020,096 B | 1,013,602 B | 247,168 B | 51,559 B | 3,741 B |
| 1 MiB 内容较分散的文本，每次改 1 B | 22,020,096 B | 12,868,639 B | 11,388,348 B | 600,759 B | 3,741 B |
| 同上，每次分散改 10 处 | 22,020,096 B | 12,868,908 B | 11,498,421 B | 601,851 B | 5,627 B |

例如插入／删除样本，现有 Git 存储约 12.32 MiB，Git pack 约 593 KiB，逆向差分约 5.23 KiB。相对于当前 Git 存储，pack 节省约 95.3%；相对于普通目录现状节省约 97.3%。这些是指定样本的结果，不是所有项目的保证。

小文件可能是索引和摘要更大，完全重写或不可压缩内容也可能没有收益。必须比较实际编码后大小，自适应选择全文或差分。

实验中的文本压力样本并非用户会话抽样；二进制测试只证明字节编码能力，不扩展当前受支持工具或文件捕获范围。写入计时只有单次运行，Git 写入包括子进程启动，不能据此给出稳定的性能承诺。后续补充 5 次暖缓存读取的中位数，方法及边界见下方全面对比。

## 方案一：回滚专用的逆向字节差分

每次修改保存：文件路径、会话及调用身份、修改前后是否存在、原始长度、前后完整内容摘要、逆向差分或压缩后的修改前内容。保存粒度和重启持久性继续按工具调用提供。

还原步骤：

1. 读取当前文件，核对存在状态、长度及修改后摘要。
2. 从当前内容执行逆向差分，或读取压缩后的修改前全文。
3. 核对重建后的修改前长度及摘要。
4. 沿用现有执行前再次核验、原子写回、进度记录和完成结果保存。

同一文件连续修改时，从最新修改后内容逐步逆推；每步验证摘要，防止跳过用户插入的修改。新建文件如果目标之前不存在，验证修改后内容后删除；空文件与不存在必须分别表示。

此路线不需要额外保存每一版修改后全文。若当前文件不匹配，就保留当前文件并报告无法还原；不能模糊应用补丁或仅按修改时间判断。它支持重启后撤销，因为持久差分和工作文件共同构成恢复依据，但不承诺脱离工作文件浏览任意历史版本。

当前 `prepare` 先从独立 before/after 内容重放操作，之后才校验工作文件，顺序及接口需要重构。新清单应持有明确的逆向步骤及依赖；不能混用新的条件恢复记录与旧的独立快照引用。

本次逆向原型：同长度替换使用多个字节范围；长度变化使用共同前后缀之间的一段替换。它不是完整通用最优差分算法，多处同时插入／删除仍可能编码很大。生产方案应使用经过验证的字节差分算法、限定计算资源，并在压缩全文更小时回退。VCDIFF 是已有的字节差分规范，可作为候选格式依据。[RFC 3284](https://datatracker.ietf.org/doc/html/rfc3284)

## 方案二：保存独立版本，交给 Git 做差分打包

Git pack 可以存放完整压缩对象及相对于其他对象的差分，读取时仍返回完整原文。显式提供内容地址列表即可覆盖当前 JSON 引用的对象；私有裸仓库也可服务普通目录，不要求用户项目本身是 Git 仓库。[git-pack-objects](https://git-scm.com/docs/git-pack-objects)、[git-init](https://git-scm.com/docs/git-init)

它保留现有 `put/get` 的独立快照能力，采用成熟差分算法，对分散修改也有效。主要成本是维护压缩、读取及清理的一致性；Git 工具不可用时需要独立压缩全文的回退格式。

当前私有 blob 没有 Git 引用，外部 JSON 对 Git 的垃圾回收不可见；不能直接运行普通 `git gc` 或认为默认 `repack --all` 一定会保留全部回滚内容。需要建立私有内容引用，或由插件枚举并显式保留所有依赖对象。[git-gc](https://git-scm.com/docs/git-gc)

当前 [storage-cleanup.js](../src/storage-cleanup.js) 只扫描独立对象文件。打包后必须统计 pack、索引与共享空间，删除会话时重建保留对象集合；删除少量记录不会立即释放共享 pack 的部分字节。压缩切换要先回读验证并发布新数据，再清除旧表示，且处理跨进程读写、中断与暂存空间。[git-prune-packed](https://git-scm.com/docs/git-prune-packed)

## 其他路线

**只给全文增加压缩**：改动较小，保留去重及独立读取能力，尤其适合当前普通目录的原始内容存储；它不能消除相似版本间的重复。小文件和不可压缩文件需 raw 回退。Node.js 原生 Zstandard 于 v22.15.0 加入，本项目 `node >=22` 不能保证支持；正式格式需能力检查、可读回退或明确提高最低要求。[Node.js v22.22.1 zlib](https://nodejs.org/download/release/v22.22.1/docs/api/zlib.html)

**完整基准加有限差分链**：不依赖工作文件，可统一 Git 与普通目录；需要自己管理差分解码、基准依赖、链长和损坏边界。本次每 8 版基准原型最大解码深度 7，局部修改有效，但简单单段差分在 10 处散改样本约占 9.26 MiB，远大于 Git pack 的 588 KiB。这说明差分算法比「是否叫 diff」更重要。

**内容分块去重**：可以让多个版本共享未变化块，避免版本链；对大文件有潜力，但增加块索引、对象数量和清理成本。本次未做分块基准，不给出节省比例。[Borg 官方数据结构说明](https://borgbackup.readthedocs.io/en/stable/internals/data-structures.html)

**合并重复观察及减少小文件数量**：可以降低元数据和磁盘分配开销，但不能在尚可回滚到中间用户消息时丢弃所需中间修改。按当前产品规则定义保留范围之后才能删，不应将空间优化变成静默缩短还原历史。

## 已验证与尚未验证

已完成 8 个场景、每场景 21 个版本、6 种表示的逐字节回读。独立快照重新创建读取实例；差分索引从磁盘重新读取；pack 回读从只放 pack/idx、没有 loose 副本的新裸仓库完成。逆向方案从最新工作内容重建全部前序版本。另测试中文、BOM、CRLF/LF、无末尾换行、空内容和 NUL／非 UTF-8 字节；外部修改触发摘要核验失败。

这些验证证明实验格式的还原与空间结果，不等于已实现插件网关、跨窗口清理、迁移或崩溃恢复。正式实现必须补齐：

- 多个会话共享内容、清理中间会话后其余记录仍可还原。
- 重启、预览过期、部分执行、结果不确定及用户继续修改。
- 写入、压缩、清理各阶段中断，以及磁盘不足、损坏和缺失基准。
- 新旧记录共存；保留 `cas:`、`git:` 的旧读取能力。
- 正文预览与选择还原不能扩展到未经授权的历史文件读取。

建议先实现新格式双读、新写，验证和迁移完毕后再释放旧内容。若先只做全文压缩，应明确它是渐进优化；若选逆向差分，应同时明确「安全撤销」与「独立历史档案」的能力边界，不混称。

一手资料的完整核对与最小 Git 实验见：[文件回滚存储一手资料研究](rollback-storage-primary-sources-20261013.md)。

## 与现有方案的全面对比

推荐方案在此指「逆向字节差分 + 压缩修改前全文回退 + 新建文件只存删除所需信息」。它是拟议方案，实验验证了基本编码，不代表已完成生产实现。Git pack 作为保留独立历史副本的备选。

| 维度 | 现有完整快照 | 推荐逆向差分方案 | 私有 Git pack 备选 |
|---|---|---|---|
| 保存什么 | 每个不同版本的完整内容，以及会话、路径、调用及执行状态 | 撤销所需的原字节、位置和前后校验值；差分不划算时存压缩原文；新建文件不备份新全文 | 独立版本在逻辑上完整，物理上用基准和差分共同保存 |
| 小幅反复修改 | 每个不同版本都有一份全文；仅相同版本去重 | 通常只增加差异及少量记录，收益最大 | 相似版本共享大部分内容，收益明显 |
| 新建大文件 | 另外保存新文件完整内容 | 单纯删除撤销只需不存在标记、后状态长度及摘要；后续编辑另存撤销所需信息 | 初始新内容至少要保存一份，压缩是否有效取决于内容 |
| 小文件／大幅重写 | 简单稳定，小文件可能更划算 | 需要比较大小并回退；完全重写可能仍需近乎完整原文 | 小文件有索引开销；完全重写可能几乎无节省 |
| 连续修改的还原 | 读取目标前后快照；预览准备仍需要扫描、核验相关调用 | 可能要从当前内容逐步撤销多次修改，必须保持顺序并逐步核验 | Git 解码到所需完整对象；链长可以限制 |
| 当前文件后来被用户修改 | 自动还原拒绝，但独立历史内容仍在 | 同样拒绝，纯差分记录通常无法再独立重建完整历史；全文回退记录可保留其前内容 | 自动还原仍拒绝，历史内容保持独立 |
| 当前文件丢失／损坏 | 独立快照仍可读；现有自动还原仍要求当前状态匹配，不能因此擅自覆盖 | 对依赖当前内容的记录无法重建；新建文件删除目标已不存在也需按既有状态规则处理 | 独立版本仍可读；自动还原规则不变 |
| 重启 | 已实现持久恢复 | 可以支持，但差分、身份与状态都要先可靠保存；必须补插件集成测试 | 可以支持，需确保对象保留、索引可读及压缩切换可靠 |
| 中文／BOM／换行 | 保存原字节，已在当前实现验证 | 必须使用字节差分；原型逐字节验证通过，不能直接拿展示用行 diff 存档 | Git blob/pack 保留原始字节；已验证隔离回读 |
| 数据损坏影响 | 独立对象损坏一般影响引用该对象的记录；不会因版本顺序牵连其他独立对象 | 某段撤销记录损坏，可阻断需要经过它的更早恢复路径 | 基准对象或 pack 损坏可影响多个版本；仍需内容校验和故障拒绝 |
| 安全保护 | 当前内容逐字节比对、路径检查、执行前再次核验、持久进度、结果不确定不重做 | 需保留这些保护，另核验重建前后摘要和长度、差分边界；不能模糊套补丁 | 可保留现有工作文件保护，增加打包维护和对象可达性保护 |
| 内存与 CPU | 读取完整前后内容，占用仍与文件大小有关 | 差分计算、重建及摘要需要 CPU；小磁盘占用不代表低内存，重建仍可能持有全文 | 写入、压缩打包和解码需要 CPU；pack 搜索窗口及链深需受限 |
| 跨会话清理 | 根据保留记录保护共享完整对象，机制已实现 | 撤销链若跨记录依赖，清理中间记录不能破坏仍保留的路径；可能需合并链或物化原文 | 需要重写保留对象集合；不能直接删共享 pack 的一部分 |
| 内容预览 | 底层可以独立读取版本；当前界面不等于已经提供历史正文浏览 | 当前文件有效时，可重建「当前 → 还原后」正文，符合已确认的预览范围；不提供脱离当前文件的任意历史浏览 | 可读取独立版本，较容易保留未来历史浏览能力 |
| 新旧数据迁移 | 无新增迁移要求 | 观察、准备、预览、执行及清理需适配新格式；旧快照继续可读，安全验证后再释放 | 快照地址与读取可较多复用；清理、统计、压缩发布需较大改造 |
| 是否自动解决无限增长 | 否，无总量或过期策略 | 否，只降低增速；保留期限仍是独立产品决定 | 否，打包不等于删除无需保留的历史 |
| 当前成熟度 | 已交付，完整回归与安装验收通过 | 只有隔离原型，不应声称与当前实现同等成熟 | 差分算法成熟，本插件的管理层尚未实现 |

### 读取耗时补测

对于上述 1 MiB 插入／删除样本，连续撤销 20 次的对比：

| 方法 | 读取／重建时间中位数 |
|---|---:|
| 当前普通目录：读取初始及最新全文 | 2.89 ms |
| 独立压缩全文：读取解压初始及最新版本 | 5.61 ms |
| 逆向差分：通过 20 段撤销重建初始版本 | 24.49 ms |
| 当前 Git：两个 `cat-file` 进程读取初始及最新版本 | 86.85 ms |
| Git pack：两个 `cat-file` 进程读取初始及最新版本 | 87.19 ms |

每项在同一机器执行 5 次暖缓存读取，取中位数；逆向方案以已读取的当前文件作为起点，独立方案读取两个保存的对象。均不包含网关、完整调用重放、工作文件安全读取／写回、结果保存或界面渲染。普通 CAS 现有地址校验由真实读取函数完成；其他独立方案在原型中核验解码后摘要及字节相等。Git 时间含每次子进程启动，不能把这个差异全归于存储算法，也不能将它视为整体回滚速度。

补测表明：逆向差分比简单全文读取增加重建成本；它在当前 Git 子进程调用方式下仍可能更快。正式实现需要对长历史、大文件及并发场景再测，不能承诺「省空间就一定快」。

### 选型判断

- 如果首要目标是降低回滚存储，且继续要求当前文件匹配才允许还原，逆向差分方案最贴合，尤其适合新建文件和局部修改。
- 如果需要保留独立历史副本，或希望降低损坏、文件丢失对历史读取的影响，Git pack 更均衡：空间收益大，现有快照接口可较多沿用，但不能省略清理重构。
- 如果优先控制本次改造风险，先给普通目录全文增加压缩是较小的步骤，收益有限但保留当前能力。

推荐方案并不在所有维度胜出：它换取空间节省的代价主要是当前文件依赖、链式重建成本和生命周期复杂度。是否接受这种交换，应按产品是否需要独立历史版本决定，而不是仅看最小空间数字。
