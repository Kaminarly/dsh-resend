# dsh-resend 运行存储与清理报告

核查日期：2026 年 10 月 11 日（香港时间）。对象：本仓库当前版本 `dsh-resend 0.1.0`，以及本机安装的 DSH Desktop `2.0.17`。

## 1. 先看结论

插件直接产生的长期文件集中在 **DSH 数据目录下的 `plugins/dsh-resend/`**。这里保存文件回滚清单、修改前后的完整内容和回滚完成记录。它们是功能数据，不能作为普通缓存清理。

本机这个目录目前只有 **8 份空清单，合计 16 字节**；尚未发现文件内容快照、回滚完成记录或残留的 `.pending` 文件。当前没有必要通过删除插件数据来释放空间。

可以优先考虑清理的是：退出应用后的旧诊断日志、应用的可重建缓存，以及确认不再需要的开发测试文件。当前开发临时目录约 **210.23 MiB**，远大于插件自己的运行数据，但其中包含两个 Git 目录，不能整目录盲删。

必须保留的是：需要继续使用的会话记录、Profile 配置、已安装插件文件，以及仍需文件回滚功能的清单和内容快照。**尤其不能只删 `outcomes/`：这会丢失「该回滚已经执行过」的依据。**

## 2. 路径与统计口径

报告使用以下缩写，后面的路径都可按此展开。

| 缩写 | 含义 | 本机路径 |
| --- | --- | --- |
| `H` | DSH 数据目录；插件读取进程的 `DSH_HOME`，未设置或为空时使用用户目录下的 `.dsh` | `C:\Users\Administrator\.dsh` |
| `P` | 插件自己的运行数据目录 | `C:\Users\Administrator\.dsh\plugins\dsh-resend` |
| `A` | Desktop 应用数据目录 | `C:\Users\Administrator\AppData\Roaming\DSH Desktop` |
| `R` | 当前源码仓库 | `D:\Code\MJ-Project\dsh-resend-2` |

Desktop 可选择其他数据目录，启动时会把选中的目录传给插件。因此，修改过数据目录时，应以应用实际使用的目录为准。`A` 与 `H` 是两个不同目录：移动 DSH 数据目录不意味着日志和浏览器缓存也随之移动。

本机未发现 Desktop 的自定义数据目录选择记录，默认 `H` 下也存在实际插件数据。仓库与已安装插件的 Host、Client 两个主要构建文件逐字节一致，因此以下行为与本机安装版本一致。

体积以文件内容长度统计：1 KiB = 1,024 字节，1 MiB = 1,048,576 字节。**不等同于磁盘实际占用**，未计入目录开销和小文件分配单元，也未对硬链接去重；符号链接和目录联接未跟随。小文件很多时，实际占用可能明显高于内容长度。现场数据是核查时的快照，使用中会继续变化。

## 3. 插件直接产生的文件

| 文件或目录 | 何时产生、保存什么 | 体积依据 | 删除条件与后果 |
| --- | --- | --- | --- |
| `P\records\<64位摘要>.json` | 编辑重发或重新生成提交前，为这次回退建立文件清单；保存文件路径、前后内容的引用，或无法回滚的原因 | 没有涉及文件时为 `[]`，**2 字节**。单文件模拟为 **180 字节**；文件越多、路径越长，清单越大 | **保留历史文件回滚时不能删。** 删除后，对应回退点无法读取文件清单；即使内容快照还在，也无法正常发起该点的回滚 |
| `P\objects\<64位 SHA-256 摘要>` | 非 Git 工作目录，或找不到 Git 程序时，保存可回滚文件修改前后的完整内容；没有文件后缀 | **不压缩，体积等于原文件版本的字节数**。相同内容在同一存储中只保存一份 | **仍被清单引用时不能删。** 删除后对应文件无法恢复。不能根据文件旧、没有后缀或像随机名字判断它无用 |
| `P\objects.git\` | 工作目录属于 Git 仓库时，创建插件专用的内容仓库，保存前后版本；与项目自身的 `.git` 分开 | 本机模拟初始开销 **26,267 字节，约 25.65 KiB**；内容会压缩，实际体积取决于文件内容和本机 Git 配置 | **保留历史文件回滚时不能删。** 不要在这里运行 `git gc`、`git prune` 等常规清理：对象没有 Git 分支引用，JSON 清单中的引用不能保护它们免于被清理 |
| `P\outcomes\<64位摘要>.json` | 文件回滚完整执行成功后，保存结果和「已完成」状态，重启后仍会读取 | 单文件模拟为 **135 字节**；数量、路径和拒绝原因会影响大小 | **保留回滚完成状态时不能删。** 删除后重启应用，会忘记该点已执行；当工作文件再次符合旧的修改后内容时，可以重新生成恢复计划 |
| `P\records\<摘要>.json.<UUID>.pending` | 清单保存过程中暂存 JSON，然后改名为正式文件 | 与该清单近似；正常成功后不留下临时副本 | **全部相关 DSH 进程退出后，确认是中断残留才可删。** 它不会被正常读取为正式清单；如果正式文件缺失，可先留作排查或恢复材料 |
| `P\outcomes\<摘要>.json.<UUID>.pending` | 回滚结果保存过程中暂存 JSON，然后改名为正式文件 | 与对应结果近似；正常成功后消失，保存失败时也会尝试删除 | **同样只在进程退出并确认残留后清理。** 如果文件已恢复但正式结果缺失，应先保留证据，不能把删临时文件当作完成状态修复 |
| Git 自身的写入临时文件 | 写入专用 Git 内容仓库时，Git 可能在内部创建暂存对象或锁文件 | 由 Git 实现决定，无插件规定的固定体积 | 运行时不要碰；异常残留须在所有相关进程退出后检查。正式内容对象不能按临时文件处理 |

补充规则：

- `P` 不带 Profile 名称，同一个 `H` 中的不同 Profile 共用这个存储位置。清理影响可能超出当前窗口或当前 Profile。
- 文件名使用会话 ID 与回退点 ID 的摘要，不能直接从文件名看出属于哪条会话。
- 仅开启插件、正常浏览会话、观察工具写文件，不会立即写出这些内容快照；写文件前后的内容先保存在内存中。编辑重发或重新生成提交时，才将涉及的内容保存到磁盘。
- 即使没有可回滚文件，也会为一次正常提交建立 2 字节空清单。恢复旧会话时没有现场观察到的原内容，可能只记录拒绝原因，不能保证生成完整快照。
- 插件只识别 `write`、`edit`，以及 `str_replace_editor` 的创建、替换、插入操作。任意命令行修改文件，不因此获得快照保证。
- 同一文件在被撤回范围内多次修改，清单保存这一段的最初内容和最后内容，不为每一次中间修改单独建版本。创建前不存在的文件用 `null` 表示，不生成「不存在」的内容文件。
- 预览和取消回滚只建立、清除内存中的计划，不新增独立预览文件。**成功执行回滚后，原清单和内容快照仍保留。**
- 插件的操作锁、界面计算缓存和待执行计划均在内存中，没有对应的独立磁盘缓存或插件锁文件。工具观察会保留完整前后内容，可能增加内存占用，但不能通过删除磁盘缓存释放这部分内存。
- 当前没有按天数、总容量或文件数量自动清理的机制，也没有单文件快照大小上限。提交失败时，代码会在确认回退记录未写入会话后移除清单，但已写出的内容对象可能保留。
- 清单保存过程发生异常时，`.pending` 没有完整的兜底清理；进程意外退出也可能留下残留。结果文件的保存失败分支会尝试移除自己的 `.pending`。

| --- | --- | --- | --- |

| 会话工作目录中的实际文件 | 执行文件回滚时，插件把旧内容写回原路径；回滚新建文件时会删除原文件 | 由用户文件决定，没有固定大小 | **这是工作成果，不是临时数据。** 不能以插件清理为理由删除 |

日志限制来自本机 Desktop 版本：主进程和独立 Host 的日志写入器均按 **10 MiB/文件**轮换，并对各自直接管理的日志文件集合设置 **200 MiB** 容量限制。主进程启动时清理超过 **7 天**的旧日志；独立 Host 日志初始化未见同样的按天清理调用。本机 `logs/host` 中仍有更早的日志，不能假定所有日志都会在 7 天后消失。

日志系统按级别筛选内容，不保证每一条插件信息都落盘。警告可能同时写入普通日志和错误日志，但体积仍属于宿主共享日志。

**编辑或重新生成不会缩小原会话文件。** 旧内容仍在记录中，只是在有效对话和界面显示上被替换。重复重新生成还会保存新的回复和工具输出，因此会话文件可能持续增长；每次增长取决于被引用记录的数量、新消息长度、生成内容及压缩效果，没有统一的「每次多少 KB」。

## 6. 文件体积如何估算

### 6.1 内容快照通常是主要增量

非 Git 存储中，一个之前存在的文件从 `B` 字节改到 `A` 字节，首次记录这两个不同版本需要约 **`B + A` 字节**，再加清单。若某个版本已存储，重复内容不再增加；若为新建文件，只需保存新内容。

例如，一份 1 MiB 文件修改前后各约 1 MiB，首次建立回滚记录，非 Git 内容存储约增加 **2 MiB**。100 次回退如果每次都是两个互不重复的 1 MiB 版本，约增加 **200 MiB**，另加清单和结果；这是条件明确的估算，不是固定配额。连续版本重复、文件未变化时，占用会更少。

Git 内容存储也保存完整前后内容，但会压缩。当前插件没有主动打包或计算版本差异，不能按「只保存改动的几行」估算；也不能假定每种文件都有相同压缩率。

### 6.2 本机模拟结果

以下测试使用真实内容存储，读取后核对字节，并重复写入验证去重。表中 Git 列只计入内容新增量，不包含首次建立专用仓库的约 25.65 KiB 开销。

| 原始文件大小 | 非 Git：内容对象大小 | Git：全是重复字符 | Git：随机可打印文本 |
| --- | --- | --- | --- |
| 1 KiB | 1,024 字节 | 28 字节 | 887 字节 |
| 100 KiB | 102,400 字节 | 484 字节 | 85,324 字节，约 83.32 KiB |
| 1 MiB | 1,048,576 字节 | 4,613 字节，约 4.50 KiB | 874,017 字节，约 853.53 KiB |

重复字符属于压缩效果很好的样本，随机文本属于压缩效果较弱的样本；两者说明体积受内容影响，不代表业务文件的平均压缩率。Git 初始化体积也会随版本和模板变化。

## 7. 清理时按这个顺序判断

1. **先退出 DSH Desktop，以及使用同一个数据目录的其他 DSH 进程。** 开发临时文件则先结束测试、探测和预览服务。不要在正在回滚或保存设置时删文件。
2. **先处理可重建或已经结束的资料。** 不再用于排查的旧日志、明确的应用缓存目录、结束的测试 Profile、无需保留的页面快照，可以分别清理。不要把 `Local Storage`、`Network`、Profile 或整个应用数据目录一并删除。
3. **保留当前配置和安装来源。** 插件配置通过设置页重置；安装文件通过插件页卸载。旧安装包和备份仅在无需恢复时删除。
4. **处理 `.pending`、`.tmp` 时确认它只是残留。** 插件不会把 `.pending` 自动恢复为正式文件。若正常清单或回滚结果缺失，先保留副本用于排查，尤其是已经改回工作文件却未成功保存结果的情况。
5. **需要释放内容快照时，先明确是否放弃历史文件回滚。** 当前没有自动判断对象是否仍被引用的清理工具。不要只删 `objects/`、`objects.git/` 的部分文件，也不要只删 `outcomes/`。
6. **确实放弃全部历史文件回滚时，先完整备份 `P`，再在停止所有使用者后整体移除该目录。** 这不会清空宿主会话，但会失去旧回退点的文件内容和已完成状态；重新启用后只会为后续操作建立新记录，旧记录不会从会话自动完整补回。这里只说明可行条件，本次没有执行清理。
7. **需要删除会话时，优先使用宿主的会话删除功能。** 当前插件代码没有在会话删除后清理对应私有清单、内容和结果的联动机制，不应假定删除会话会同步回收插件快照。

对当前机器，清理优先级应是：**确认结束的开发测试资料 → 无需留存的日志和缓存 → 旧安装包与备份**。插件私有目录只有 16 字节，删除收益很小。
